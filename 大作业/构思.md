# 选题名称：SoleVault —— 基于 openGauss 的球鞋资产与收藏管理系统

## 1. 项目背景与应用需求
* **核心定位：** 一个面向球鞋爱好者的“进销存”+“图鉴”管理系统。
* **解决痛点：** 解决球鞋收藏者无法区分“鞋款档案”与“实际库存”（如同一款鞋有两双，一双穿一双藏）、难以统计总投入成本、以及缺乏个性化展示空间的问题。
* **技术侧重：** 重点展示 openGauss 在 **JSONB（半结构化数据）**、**触发器（自动化统计）** 和 **数据完整性** 方面的能力。

---

## 2. 数据库设计 (Schema Design)
> **实体数量：** 6 个（满足 ≥5 个的要求）。
> **设计特点：** 严格遵循 3NF 范式，将公共资料与个人资产分离。

1.  **`Brand` (品牌表)**
    * `brand_id` (PK), `english_name`, `chinese_name`, `logo_url`.
    * *用途：* 下拉菜单筛选、分类统计。

2.  **`Sneaker` (球鞋公共档案表)**
    * `sneaker_id` (PK), `brand_id` (FK), `model_name` (如 Air Jordan 1), `colorway` (配色名), `sku_code` (货号), `release_date`.
    * `specs` (**JSONB**): 存储非固定参数，如 `{"material": "Patent Leather", "technology": "Zoom Air", "designer": "Tinker"}`。
    * *用途：* 系统的基础数据库，一次录入，多次引用。

3.  **`InventoryItem` (个人库存/实物表) —— **核心表****
    * `item_id` (PK), `user_id` (FK), `sneaker_id` (FK).
    * `size` (尺码), `condition` (状态: New/Used), `status` (流转状态: Owned/Shipping/Sold/Wishlist).
    * `purchase_price` (买入价), `sold_price` (卖出价), `acquired_date`.
    * *用途：* 记录用户实际拥有的每一双鞋实体。

4.  **`Collection` (收藏夹表)**
    * `collection_id` (PK), `user_id` (FK), `name` (如“2024必入系列”), `is_public` (是否公开).
    * *用途：* 自定义分类容器。

5.  **`CollectionItem` (收藏夹明细表)**
    * `id` (PK), `collection_id` (FK), `item_id` (FK), `note` (个性化备注).
    * *用途：* 实现多对多关联。

6.  **`User` (用户表)**
    * `user_id` (PK), `username`, `password`, `role`.
    * `total_assets` (**冗余字段**，由触发器维护，记录当前持有资产总额).

---

## 3. 关键业务逻辑 (openGauss 特性)

### 3.1 触发器 (Trigger)：实时资产计算
* **逻辑：** 每当 `InventoryItem` 表发生 `INSERT` (买入新鞋) 或 `UPDATE` (修改价格/卖出) 时，自动计算该用户所有 `status='Owned'` 的鞋子总价，并更新 `User` 表的 `total_assets` 字段。
* **代码体现：** PL/pgSQL 函数 + Trigger 定义。
* **优势：** 避免每次刷新首页都进行全表求和，体现高性能设计。

### 3.2 JSONB 查询：灵活属性检索
* **逻辑：** 利用 openGauss 的 JSONB 操作符，查询特定属性。
* **SQL 示例：** `SELECT * FROM Sneaker WHERE specs ->> 'designer' = 'Kanye West';`
* **优势：** 解决不同品牌球鞋属性字段不统一的问题。

### 3.3 视图 (View)：隐私隔离
* **视图名：** `vw_public_collections`
* **逻辑：** 只查询 `Collection` 表中 `is_public = true` 的记录及其关联的鞋款图片和名称。
* **优势：** 前端直接调用视图，无需在代码层过滤隐私数据。

## 4. 功能模块

1.  **我的鞋柜 (Inventory)：**
    * 数据表格展示：支持按“买入价”排序、按“品牌”筛选。
    * 操作：新增库存（关联 Sneaker 表）、标记售出（输入售出价，触发状态变更）。
2.  **资产概览 (Dashboard)：**
    * 数字看板：总资产、总库存数。
    * 图表：品牌占比饼图（ECharts）。
3.  **球鞋资料库 (Library)：**
    * 展示鞋款列表，显示 JSONB 解析出的详细参数。
    * 搜索功能。
4.  **收藏展示 (Gallery)：**
    * 创建收藏夹，将库存里的鞋子加入收藏夹，生成公开展示页。

## 5. 两人分工方案

由于只有两人，建议 **全栈分工** 但各有侧重（一人偏重后端与数据库实现，一人偏重前端与数据应用）。

### 成员 A：架构、数据库与后端 API
**主要职责：核心逻辑实现与系统稳定性**
1.  **数据库建设：**
    * 搭建 openGauss 环境。
    * 编写所有 DDL (Create Table) 脚本，确保外键约束正确。
    * **关键产出：** 编写存储过程和 **Trigger (触发器)** 实现资产自动更新逻辑。
2.  **后端开发：**
    * 搭建后端框架 (Spring Boot 或 Node.js/Python)。
    * 编写 API 接口 (RESTful)，处理前端发来的 CRUD 请求。
    * 编写 **View (视图)** SQL，供公开展示页调用。
3.  **报告撰写：**
    * 负责实验报告中的“数据库设计”、“ER 图”、“核心 SQL 源码分析”部分。

### 成员 B：前端交互、数据工程与演示
**主要职责：用户体验、数据填充与可视化**
1.  **前端开发：**
    * 搭建 Web 页面 (Vue/React + UI组件库)。
    * 实现资产仪表盘的图表 (ECharts)，对接后端数据。
    * 实现 JSONB 数据的动态渲染（把数据库里的 JSON 字符串变成漂亮的参数列表）。
2.  **数据工程：**
    * **关键产出：** 负责搜集并整理 50+ 条真实的球鞋数据（包括复杂的 JSON 属性），编写 SQL 导入脚本。没有真实数据，系统演示会很空洞。
3.  **测试与演示：**
    * 进行功能测试（如：验证卖出一双鞋后，总资产是否自动减少）。
    * 录制系统演示视频。
    * 负责实验报告中的“需求分析”、“系统界面展示”、“使用说明”部分。

在报告中，你们需要特意强调**“高效的分工”**和**“技术深度”**：

    * 展示 **JSONB** 字段的设计，说明这是 openGauss 相比传统 SQL 的优势。
* **在“系统实现”章节：**
    * 成员 A 贴出 **Trigger** 的完整代码，并配上截图证明：“修改库存表 -> 用户表余额自动变化”。
    * 成员 B 贴出前端解析 JSON 数据的逻辑，以及 ECharts 图表的截图。
* **在“总结”章节：**
    * 提到两人如何配合：A 负责底层数据逻辑的强一致性（事务、约束），B 负责上层数据的可视化表现。
