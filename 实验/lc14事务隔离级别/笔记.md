# 数据库事务隔离级别实验笔记

## 实验目标
通过实际案例演示不同事务隔离级别对并发事务的影响，包括脏读（Dirty Read）、不可重复读（Non-repeatable Read）和幻象读（Phantom Read）现象。

---

## 实验示例1：读"脏"数据的实例

### 实验设置
- **事务1（查询1）**：更新 `TEACHERS` 表中 `TID='200003125'` 的 `salary`，延时20秒后回滚
- **查询2**：在事务1执行过程中查询 `salary`，延时20秒后再次查询

### 事务1代码
```sql
use School
go
BEGIN TRAN
UPDATE TEACHERS SET SALARY=4200 WHERE TID='200003125'
WAITFOR DELAY '00:00:20' -- 延时20秒
SELECT * FROM TEACHERS WHERE TID='200003125'
ROLLBACK TRAN
SELECT * FROM TEACHERS WHERE TID='200003125'
```

### 执行结果
- **事务执行过程中**：`salary = 4200`（已更新但未提交）
- **事务回滚后**：`salary = 3928`（回滚到初始值）

### 问题说明
如果查询2在事务1的20秒延时期间读取数据，会读到未提交的 `salary=4200`，这就是"脏数据"（Dirty Data）。由于事务1最终回滚，查询2读到的数据实际上是不正确的。

---

## 实验示例2：READ UNCOMMITTED 隔离级别

### 隔离级别说明
- **READ UNCOMMITTED**：事务隔离的最低级别
- **特点**：仅保证不读物理损坏的数据，允许读未提交的数据

### 查询2代码（修改后）
```sql
use School
go
SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED -- 事务隔离的最低级别
-- 模拟实现脏读
SELECT * FROM TEACHERS WHERE TID='200003125'
IF @@ROWCOUNT<>0
BEGIN
    WAITFOR DELAY '00:00:20'
    -- 模拟实现不可重复读
    SELECT * FROM TEACHERS WHERE TID='200003125'
END
```

### 执行结果
- **第一次查询**：`salary = 4200`（读"脏"数据，查询的是事务1没有提交前的数据）
- **延时20秒后再次查询**：`salary = 3928`（与第一次查询结果不一样）

### 观察到的现象
1. **脏读（Dirty Read）**：第一次查询读到了事务1未提交的数据（4200）
2. **不可重复读（Non-repeatable Read）**：同一事务中两次查询同一数据，结果不一致

### 原因分析
事务1更新数据过程与查询2的执行过程没有隔离开来，导致查询2可以读取到事务1未提交的修改，以及事务1回滚后的数据变化。

---

## 实验示例3：READ COMMITTED 隔离级别

### 解决方案
将查询2的隔离级别改为 **READ COMMITTED**（提交读），可保证不读到脏数据。

### 查询2代码（修改后）
```sql
use School
go
SET TRANSACTION ISOLATION LEVEL READ COMMITTED -- 事务隔离级别为"READ COMMITTED",提交读
-- 模拟实现脏读
SELECT * FROM TEACHERS WHERE TID='200003125'
IF @@ROWCOUNT<>0
BEGIN
    WAITFOR DELAY '00:00:20'
    -- 模拟实现不可重复读
    SELECT * FROM TEACHERS WHERE TID='200003125'
END
```

### 执行结果
- **第一次查询**：`salary = 3928`
- **延时20秒后再次查询**：`salary = 3928`
- **结论**：两次查询结果为事务1提交后的值

### 效果说明
使用 `READ COMMITTED` 隔离级别后：
- ✅ **解决了脏读问题**：查询2不会读取到事务1未提交的数据
- ✅ **读取已提交数据**：只能读取到其他事务已提交的数据
- ⚠️ **仍可能出现不可重复读**：如果事务1在两次查询之间提交了修改，仍会导致不可重复读

---

## 实验示例3补充：READ COMMITTED 下的不可重复读

### 实验设置
- **事务3（查询3）**：设置隔离级别为 `READ COMMITTED`，在事务中查询 `salary`，延时20秒后再次查询
- **查询4（代码4）**：在事务3执行过程中，更新 `salary` 并提交

### 代码3（事务3）
```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED
BEGIN TRAN
SELECT * FROM TEACHERS WHERE TID='200003125' -- 第一次查询
IF @@ROWCOUNT<>0
BEGIN
    WAITFOR DELAY '00:00:20' -- 延时20秒
    -- 模拟实现不可重复读
    SELECT * FROM TEACHERS WHERE TID='200003125' -- 第二次查询
END
ROLLBACK TRAN
```

### 代码4（查询4）
```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED
UPDATE TEACHERS SET SALARY=4200 WHERE TID='200003125'
```

### 执行结果
- **第一次查询**：`salary = 3928`
- **延时20秒后再次查询**：`salary = 4200`（查询4已更新并提交）
- **结论**：两次查询结果不同，发生了"不可重复读"

### 原因分析
同一事务中两次相同数据读取之间，"提交读"允许其他事务在两次读取的间隙修改资源，所以导致读取不一致的现象。

**注意**：SQL Server 默认隔离级别为 `READ COMMITTED`。

---

## 实验示例4：REPEATABLE READ 隔离级别

### 解决方案
为了解决示例3中"不可重复读"的问题，设置 **REPEATABLE READ**（可重复读）隔离级别。

### 代码3（修改后）
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ -- 可重复读级别
BEGIN TRAN
SELECT * FROM TEACHERS WHERE TID='200003125' -- 第一次查询
IF @@ROWCOUNT<>0
BEGIN
    WAITFOR DELAY '00:00:20' -- 延时20秒
    -- 模拟实现不可重复读
    SELECT * FROM TEACHERS WHERE TID='200003125' -- 第二次查询
END
ROLLBACK TRAN
```

### 代码4（查询4，尝试更新）
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
UPDATE TEACHERS SET SALARY=4500 WHERE TID='200003125'
```

### 执行结果
- **第一次查询**：`salary = 4200`
- **延时20秒后再次查询**：`salary = 4200`（与第一次查询结果相同）
- **结论**：保证了读一致性，解决了不可重复读问题

### 效果说明
使用 `REPEATABLE READ` 隔离级别后：
- ✅ **解决了不可重复读问题**：同一事务中多次读取同一数据，结果保持一致
- ✅ **防止其他事务修改已读取数据**：在事务结束前，其他事务无法修改已被读取的数据
- ⚠️ **仍可能出现幻象读**：虽然已读取的数据不能修改，但可能出现新插入或删除的记录

## 实验示例5：REPEATABLE READ 的局限性 - 幻象读

### 实验设置
- **代码5（事务1）**：设置隔离级别为 `REPEATABLE READ`，插入一条记录，然后查询该记录，延时10秒后再次查询
- **代码6（事务2）**：在代码5执行过程中，删除代码5查询的记录

### 代码5（事务1）
```sql
INSERT INTO TEACHERS VALUES ('300000000', 'AA', 'BBB@163.COM', 5000)
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
BEGIN TRAN
SELECT * FROM TEACHERS WHERE TID='300000000' -- 第一次查询
IF @@ROWCOUNT<>0
BEGIN
    WAITFOR DELAY '00:00:10' -- 延时10秒
    SELECT * FROM TEACHERS WHERE TID='300000000' -- 第二次查询
END
ROLLBACK TRAN
```

### 代码6（事务2）
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
DELETE FROM TEACHERS WHERE TID='300000000'
```

### 执行结果
- **第一次查询**：返回记录 `TID='300000000'`，`salary = 5000`
- **延时10秒后再次查询**：仍然返回记录 `TID='300000000'`，`salary = 5000`
- **实际情况**：代码6已经删除了这条记录
- **结论**：发生了"幻象读"（Phantom Read）问题

### 问题说明
虽然两次查询结果相同，但事实上，结果显示的记录已经被删除。`REPEATABLE READ` 只能保证已读取的数据不被修改，但无法防止其他事务插入或删除新记录，导致出现幻象读。

---

## 实验示例6：SERIALIZABLE 隔离级别

### 隔离级别说明
- **SERIALIZABLE**：事务隔离的最高级别
- **特点**：确保事务完全隔离，保证并发事务可串行化执行
- **效果**：在事务完成前，防止其他事务更新或插入数据

### 实验设置
- **代码7（事务1）**：设置隔离级别为 `SERIALIZABLE`，查询 `TID='300000000'`，延时10秒后再次查询
- **代码8（事务2）**：在代码7执行过程中，尝试插入 `TID='300000000'` 的记录

### 代码7（事务1）
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE
BEGIN TRAN
SELECT * FROM TEACHERS WHERE TID='300000000' -- 第一次查询
WAITFOR DELAY '00:00:10' -- 延时10秒
SELECT * FROM TEACHERS WHERE TID='300000000' -- 第二次查询
ROLLBACK TRAN
```

### 代码8（事务2）
```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE
INSERT INTO TEACHERS VALUES ('300000000', 'AA', 'BBB@163.COM', 5000)
```

### 执行结果
- **第一次查询**：返回空结果（无记录）
- **延时10秒后再次查询**：返回空结果（无记录）
- **代码8的执行**：被阻塞，直到代码7完成

### 结论
事务执行顺序是完全串行的，事务7在执行过程中防止代码8向其插入数据，所以查询为空。`SERIALIZABLE` 隔离级别通过范围锁（Range Lock）防止了幻象读，确保事务的完全隔离。

## 总结对比

| 隔离级别 | 脏读 | 不可重复读 | 幻象读 | 说明 |
|---------|------|-----------|--------|------|
| **READ UNCOMMITTED** | ✅ 允许 | ✅ 允许 | ✅ 允许 | 最低级别，仅保证不读物理损坏数据 |
| **READ COMMITTED** | ❌ 禁止 | ✅ 允许 | ✅ 允许 | SQL Server 默认级别，保证不读脏数据，只读已提交数据 |
| **REPEATABLE READ** | ❌ 禁止 | ❌ 禁止 | ✅ 允许 | 保证同一事务中多次读取同一数据结果一致，但可能出现幻象读 |
| **SERIALIZABLE** | ❌ 禁止 | ❌ 禁止 | ❌ 禁止 | 最高级别，完全隔离，保证事务可串行化执行 |

### 关键概念

#### 1. 脏读（Dirty Read）
- **定义**：读取到其他事务未提交的数据
- **示例**：事务A更新数据但未提交，事务B读取到该未提交的数据，随后事务A回滚

#### 2. 不可重复读（Non-repeatable Read）
- **定义**：同一事务中多次读取同一数据，结果不一致
- **原因**：在两次读取之间，其他事务修改并提交了该数据
- **示例**：事务A第一次读取 `salary=3928`，事务B更新为 `salary=4200` 并提交，事务A再次读取得到 `salary=4200`

#### 3. 幻象读（Phantom Read）
- **定义**：同一事务中多次执行相同查询，返回的记录数量或内容不一致
- **原因**：在两次查询之间，其他事务插入了新记录或删除了记录
- **示例**：事务A查询 `TID='300000000'` 存在，事务B删除该记录，事务A再次查询仍能看到该记录（已被删除）

#### 4. 事务隔离级别选择原则
- **性能 vs 一致性**：隔离级别越高，一致性越好，但并发性能越低
- **实际应用**：
  - `READ COMMITTED`：大多数应用场景的默认选择，平衡性能和一致性
  - `REPEATABLE READ`：需要保证读取一致性的场景
  - `SERIALIZABLE`：对数据一致性要求极高的场景，如金融交易
  - `READ UNCOMMITTED`：很少使用，仅用于对数据准确性要求不高的统计场景

### 隔离级别实现机制
- **READ COMMITTED**：使用共享锁（Shared Lock），读取后立即释放
- **REPEATABLE READ**：使用共享锁，事务结束前保持锁
- **SERIALIZABLE**：使用范围锁（Range Lock），防止插入和删除操作
