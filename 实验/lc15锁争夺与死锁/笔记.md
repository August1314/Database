# SQL Server 锁争夺与死锁实验笔记

## 实验目标
通过实际案例演示SQL Server中的锁争夺（Lock Contention）和死锁（Deadlock）现象，以及相应的解决方案。

---

## 1. 演示事务对资源的争夺

### 实验设置
- **目的**：演示在REPEATABLE READ隔离级别下，事务对资源的争夺导致阻塞
- **场景**：一个连接更新数据但未提交，另一个连接尝试读取相同数据

### Step1: 建立第一个连接（更新事务，未提交）

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
BEGIN TRAN
UPDATE courses SET hour=80 WHERE cid='10001'
-- 注意：事务未提交，一直保持锁定状态
```

**执行结果**：
- 事务未提交，一直在等待
- 该事务持有对`courses`表中`cid='10001'`记录的排他锁（Exclusive Lock）

### 关键概念：REPEATABLE READ隔离级别的锁机制

**注**：设置`REPEATABLE READ`隔离级别时，如果某行在被读取之后由事务进行了修改，则该事务会获取一个用于保护该行的排他锁，并且该排他锁在事务完成之前将一直保持（即不允许其他事务对该行进行读取或者修改）。

---

## 2. 验证阻塞情况

### Step2: 建立第二个连接（查询事务，被阻塞）

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
BEGIN TRAN
SELECT * FROM courses WHERE cid='10001'
COMMIT TRAN
```

**执行结果**：
- 查询被阻塞，一直等待
- 无法获取共享锁（Shared Lock），因为第一个连接持有排他锁

### 验证进程阻塞：使用 `sp_who`

```sql
EXEC sp_who
```

**结果说明**：
- 查看`blk`列（blocking列）
- 如果`blk`列的值非0，表示该进程被阻塞
- 例如：进程54的`blk`值为58，说明进程54被进程58阻塞
- 被阻塞的进程状态为`suspended`（挂起）

**示例输出**：
| spid | status    | blk | cmd   | dbname |
|------|-----------|-----|-------|--------|
| 54   | suspended | 58  | SELECT| School |
| 58   | sleeping  | 0   | UPDATE| School |

## 3. 解决永久等待问题：使用 `lock_timeout`

### 问题
当发生锁争夺时，如果事务一直等待，会导致"永久等待"的问题。

### 解决方案：设置锁定超时时间

```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
SET lock_timeout 2000  -- 设置超时时间为2000毫秒（2秒）
BEGIN TRAN
SELECT * FROM courses WHERE cid='10001'
COMMIT TRAN
```

**执行结果**：
- 如果2秒内无法获取锁，锁定管理器将自动解除锁的争夺
- 返回错误信息：
  - **错误代码**：1222
  - **消息**：已超过了锁请求超时时段。（The lock request timeout period has been exceeded.）

**说明**：
- `lock_timeout`：设置锁定超时时间间隔（单位：毫秒）
- 超时后，锁定管理器将自动解除锁的争夺
- 避免了事务永久等待的问题

## 4. 演示事务间的死锁

### 实验设置
打开两个连接，同时执行相同的代码，观察死锁现象。

### 死锁演示代码

**连接1和连接2都执行**：
```sql
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ
BEGIN TRAN
SELECT * FROM TEACHERS WHERE TID='200003125'  -- 获取共享锁
WAITFOR DELAY '00:00:05'  -- 延时5秒，为死锁创造条件
UPDATE TEACHERS SET SALARY=4000 WHERE TID='200003125'  -- 尝试转换为排他锁
COMMIT TRAN
SELECT * FROM TEACHERS WHERE TID='200003125'
```

### 执行结果

**连接1**：
- ✅ 执行成功
- 成功更新`SALARY`为4000
- 事务正常提交

**连接2**：
- ❌ 执行失败
- 由于死锁，直接停掉了当前程序工作
- 事务被回滚

### 死锁错误信息

**错误代码**：1205

**错误消息**：
```
消息 1205,级别 13,状态 51,第 5 行
事务(进程 ID 53)与另一个进程被死锁在锁资源上,并且已被选作死锁牺牲品。请重新运行该事务。
```

**翻译**：
Transaction (Process ID 53) was deadlocked on lock resources with another process and has been chosen as the deadlock victim. Please rerun the transaction.

## 5. 死锁产生的原因分析

### 死锁原因

**出现死锁的原因**：
因为两个连接都通过设置共享锁（shared lock）对同一数据进行查询，并尝试转换为更新锁（update lock），进而到排它锁（exclusive）以完成更新操作。但隔离级别为"可重复读"（REPEATABLE READ），在事务完成之前，两个连接不可能释放共享锁而永远无法更新，因而导致死锁。

### 死锁过程详解

1. **阶段1**：两个连接都执行`SELECT`语句
   - 连接1和连接2都获取共享锁（Shared Lock）在`TID='200003125'`的记录上

2. **阶段2**：两个连接都尝试执行`UPDATE`语句
   - 连接1尝试将共享锁升级为排他锁（Exclusive Lock）
   - 连接2也尝试将共享锁升级为排他锁
   - 由于REPEATABLE READ隔离级别，共享锁在事务完成前不能释放
   - 连接1等待连接2释放共享锁
   - 连接2等待连接1释放共享锁
   - **形成循环等待，导致死锁**

3. **阶段3**：SQL Server检测到死锁
   - SQL Server选择一个事务作为"死锁牺牲品"（Deadlock Victim）
   - 牺牲品事务被终止并回滚
   - 另一个事务继续执行并成功

## 6. 错误处理与预防措施

### 错误代码总结

| 错误代码 | 错误类型 | 说明 |
|---------|---------|------|
| **1222** | 锁超时 | 当系统发生锁争夺时，如果有事务超时，SQL Server向用户返回错误号1222 |
| **1205** | 死锁 | 当发生死锁时，如果有牺牲事务，SQL Server向用户返回错误号1205 |

### 应用程序中的错误处理

**在应用时，需要在应用程序中处理锁争夺与死锁**：
- 通过在错误处理器中捕获消息1222或1205
- 然后让应用自动重新提交事务

**示例代码逻辑**：
```sql
-- 伪代码示例
BEGIN TRY
    BEGIN TRAN
    -- 执行数据库操作
    COMMIT TRAN
END TRY
BEGIN CATCH
    IF ERROR_NUMBER() = 1222 OR ERROR_NUMBER() = 1205
    BEGIN
        -- 锁超时或死锁，自动重试
        ROLLBACK TRAN
        -- 重新提交事务逻辑
    END
    ELSE
    BEGIN
        -- 其他错误处理
        ROLLBACK TRAN
    END
END CATCH
```

### 避免死锁的策略

**关键原则**：为了避免死锁，存取资源顺序最好相同。

**示例说明**：
- 如果连接A先存取甲数据库对象，再存取乙数据库对象
- 如果连接B的存取顺序刚好相反（先存取乙，再存取甲）
- 则有可能发生死锁

**最佳实践**：
1. **统一资源访问顺序**：所有事务按照相同的顺序访问资源
2. **减少事务持有锁的时间**：尽快提交或回滚事务
3. **使用较低的隔离级别**：在满足业务需求的前提下，使用较低的隔离级别
4. **避免长事务**：将长事务拆分为多个短事务
5. **使用锁超时**：设置合理的`lock_timeout`值

## 7. 锁的类型总结

### 锁的兼容性矩阵

| 锁类型 | 共享锁(S) | 排他锁(X) | 更新锁(U) |
|--------|----------|----------|----------|
| **共享锁(S)** | ✅ 兼容 | ❌ 不兼容 | ✅ 兼容 |
| **排他锁(X)** | ❌ 不兼容 | ❌ 不兼容 | ❌ 不兼容 |
| **更新锁(U)** | ✅ 兼容 | ❌ 不兼容 | ❌ 不兼容 |

### 锁的升级过程

在REPEATABLE READ隔离级别下，UPDATE操作通常经历以下锁升级过程：
1. **共享锁（Shared Lock）**：读取数据时获取
2. **更新锁（Update Lock）**：准备更新时尝试升级
3. **排他锁（Exclusive Lock）**：实际执行更新时获取

## 8. 实验总结

### 关键概念

1. **锁争夺（Lock Contention）**
   - 多个事务同时请求同一资源的锁
   - 导致某些事务被阻塞
   - 可以通过`sp_who`查看阻塞关系

2. **锁超时（Lock Timeout）**
   - 使用`SET lock_timeout`设置超时时间
   - 超时后返回错误1222
   - 避免事务永久等待

3. **死锁（Deadlock）**
   - 两个或多个事务相互等待对方释放锁
   - SQL Server自动检测并选择一个牺牲品
   - 牺牲品事务返回错误1205并回滚

### 隔离级别与锁的关系

- **REPEATABLE READ**：在事务完成前，已读取的数据上的共享锁不会释放
- 这保证了可重复读，但也增加了死锁的可能性
- 需要权衡数据一致性和并发性能

### 最佳实践

1. ✅ 统一资源访问顺序
2. ✅ 设置合理的锁超时时间
3. ✅ 在应用程序中处理1222和1205错误
4. ✅ 尽量缩短事务执行时间
5. ✅ 根据业务需求选择合适的隔离级别
